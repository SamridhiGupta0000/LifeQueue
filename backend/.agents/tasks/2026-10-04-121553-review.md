# LifeQueue Backend Data Layer

The backend implements a full SQLite-backed REST API for LifeQueue: task CRUD, dependency management, focus sessions, analytics, and a greedy session optimizer. The priority score formula, route ordering, soft delete, and focus duration computation are all correct. Two issues need fixing before shipping: a staleness bug in `getPrioritizedTasks` where the live `score_breakdown` diverges from the stored sort key over time, and the optimizer's dependency gate treating archived tasks as incomplete blockers.

Watch for: (1) **confirmed** — `getPrioritizedTasks` recomputes `score_breakdown` live from stored fields; because urgency is time-sensitive, `score_breakdown.total` will contradict the sort order as deadlines approach. (2) **confirmed** — the optimizer checks `status !== 'done'` to clear a dependency; archived dependencies are treated as blockers, permanently suppressing dependent tasks from session recommendations with no diagnostic.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The priority formula `(impact×10) + (urgency×8) + (consequence_weight×6) - (effort_penalty×4)` is implemented exactly as specified and applied consistently at task creation, update, and seeding. Route ordering in `tasks.js` places `/prioritized` and `/dependencies` before `/:id`, preventing Express from routing static paths into the dynamic segment handler.

The circular-dependency BFS is correct: `hasPath(db, dependsOnId, taskId)` asks "does the task I'm about to depend on already transitively depend on me?" before inserting. It fetches the full edge list once, builds an adjacency list, and visits all reachable nodes — covering transitive cycles at any depth.

`getPrioritizedTasks` sorts by the stored `priority_score` column, then attaches a live `score_breakdown` via `getScoreBreakdown`. Because `getUrgency` computes urgency relative to `Date.now()`, the breakdown diverges from the stored score over time. A task stored at score 120 with urgency=8 yesterday now computes with urgency=9; the breakdown shows 128 but the task ranked at position 3 (not 1). The sort order is internally consistent but the per-task breakdown contradicts it.

The optimizer's dependency gate checks `depTask.status !== 'done'`. Archived tasks (soft-deleted via `DELETE /api/tasks/:id`) satisfy neither `'done'` nor `'not found'`, so they permanently block any dependent task from optimizer recommendations with no error or diagnostic to the caller.

`createTask` and `updateTask` validate `title`, `impact` (1–10), and `estimated_minutes` (positive integer), but neither validates the `status` field. A caller can POST a task with `status='archived'` at creation time, which would immediately hide it from `listTasks` default views and confuse the optimizer's status filter.

<summary>Issues (3)</summary>

1. **Score breakdown diverges from sort order** — `getPrioritizedTasks` re-runs `getScoreBreakdown` live on stored rows; urgency is time-sensitive so the breakdown total drifts from the stored `priority_score` driving sort order. Fix: recompute `priority_score` live in `getPrioritizedTasks` and sort on the recomputed value, so breakdown and sort key are always in sync. The stored `priority_score` column would still be useful for indexed queries that don't need a breakdown.

2. **Archived tasks block optimizer** — `optimizeSession` treats `status='archived'` as an incomplete dependency, silently preventing dependent tasks from ever appearing in session recommendations. Fix: treat `'done'` and `'archived'` as both satisfying the gate: `!['done', 'archived'].includes(depTask.status)`.

3. **No status validation on task creation** — `createTask` accepts any string as `status`, including `'archived'`. A task created with an invalid status will be invisible to normal queries and may corrupt optimizer logic. Fix: whitelist `['pending', 'in_progress', 'done']` as valid creation statuses.

### Score breakdown divergence in getPrioritizedTasks

`getPrioritizedTasks` sorts by the stored `priority_score` column, then maps each task through `getScoreBreakdown(task)`. `getScoreBreakdown` calls `getUrgency(task.deadline)`, which computes `diffDays` relative to `Date.now()`. A task created two days ago with a 3-day deadline had `urgency=8` at storage time; today with a 1-day deadline it gets `urgency=9`. The stored score drives the sort; the live breakdown contradicts it.

The fix with the smallest surface area: recompute `priority_score` live in `getPrioritizedTasks` using `calculatePriorityScore`, sort on that recomputed value, and attach the breakdown from the same computation. Ranking will then always reflect current urgency, which is the intended behaviour for "what should I do next."

### Archived dependency silently blocks optimizer

In `optimizerController.js`:

```js
const hasIncompleteDep = depIds.some((depId) => {
  const depTask = allTaskLookup[depId];
  return !depTask || depTask.status !== 'done';
});
```

`allTaskLookup` is built from `SELECT id, status FROM tasks`, which includes archived rows. An archived dependency has `status='archived'`; `'archived' !== 'done'` is `true`, so the dependent task is skipped. A user who archives a prerequisite because it's no longer relevant will find that tasks depending on it permanently disappear from every session recommendation with no explanation.

Fix: `return !depTask || !['done', 'archived'].includes(depTask.status)`.

### Status field not validated on creation

`createTask` validates `title`, `impact`, and `estimated_minutes` but not `status`. The optimizer filters `WHERE status IN ('pending', 'in_progress')`, `listTasks` filters by `status` query param, and `completeTask` unconditionally sets `status='done'` without checking current status. An arbitrary string slipping in at creation time produces no immediate error but silently falls through all these filters. The schema has no `CHECK` constraint on `status` values.

### Seed focus session time discrepancy

The seed inserts a focus session with `start_time = datetime('now','-2 hours')` and `end_time = datetime('now','-30 minutes')`, giving an elapsed time of 90 minutes (5400 seconds), but the `duration` column is hard-coded to `5400` rather than derived. The elapsed range is actually 90 minutes (120 min − 30 min), so `duration=5400` is consistent — but the comment in the seed script says "90 minutes in seconds" while the time range covers 90 minutes. No actual data corruption; worth noting that `analytics` will report 90 minutes of focus time for this session.
